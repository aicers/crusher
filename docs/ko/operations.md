# 실행

## 실행 커맨드

Crusher는 아래 형태로 실행합니다.

<!-- markdownlint-disable MD013 -->
```bash
crusher [-c <CONFIG_PATH>] --cert <CERT_PATH> --key <KEY_PATH> --ca-certs <CA1[,CA2,...]> <SERVER_NAME>@<SERVER_IP>:<SERVER_PORT>
```
<!-- markdownlint-enable MD013 -->

- `-c <CONFIG_PATH>`: TOML 설정 파일 경로
- `--cert <CERT_PATH>`: Crusher 인증서(PEM) (필수)
- `--key <KEY_PATH>`: Crusher 개인키(PEM) (필수)
- `--ca-certs <CA_CERT_PATH>[,...]`: 접속 대상 서버 검증용 CA 인증서(PEM) 목록 (필수)
- `<SERVER_NAME>@<SERVER_IP>:<SERVER_PORT>` : Manager 서버 주소 (필수)

## 로컬 설정 모드

```bash
crusher -c /path/to/crusher/config.toml \
  --cert /path/to/crusher/certs/cert.pem \
  --key /path/to/crusher/certs/key.pem \
  --ca-certs /path/to/crusher/certs/ca_cert.pem \
  manager@10.0.0.1:38390
```

## 원격 설정 모드

```bash
crusher \
  --cert /path/to/crusher/cert.pem \
  --key /path/to/crusher/key.pem \
  --ca-certs /path/to/crusher/ca_cert.pem \
  manager@10.0.0.1:38390
```

이 경우 설정은 Manager 서버에서 받아옵니다.

Manager에 이 인스턴스의 설정이 아직 없으면 Manager는 `001.crusher unregistered`
같은 사유로 요청을 거절합니다. Crusher는 이를
`Waiting for a configuration from the Manager: <사유>` 경고로 기록하고 유휴
모드에서 기다립니다. 인스턴스를 설정하기 전에는 정상적인 동작이며, Manager가
설정을 보내면 Crusher가 바로 시작합니다.

## 윈도가 기록되는 시점

Crusher는 정책의 시계열을 윈도(주기 하나) 단위로, 정책의 모든 센서가 윈도의
끝을 지난 뒤에 기록합니다.

- 정책은 센서마다 Data Store에서 스트림을 하나씩 받아, 모든 센서의 이벤트를
  같은 윈도에 더합니다. 스트림이 시작되면 Data Store는 먼저 정책이 이어서
  시작하는 시점부터 저장된 이벤트를 다시 보내고(재생), 재생이 끝났음을 알린
  뒤, 새로 들어오는 이벤트를 보냅니다.
- 센서의 스트림은 윈도가 끝나고 900초가 넘은 시각의 이벤트를 보내면, 재생
  중이든 아니든 그 윈도를 지난 것으로 봅니다. Crusher는 늦게 도착하는 센서
  묶음과 시계 차이를 고려해 윈도가 끝나고 900초를 기다립니다. 센서는 이벤트를
  최대 600초 단위로 묶어 보냅니다.
- 이벤트가 없는 스트림은 재생이 끝났고, 30초 동안 이벤트가 도착하지 않았으며,
  시계가 윈도의 끝에서 900초 이상 지났을 때 그 윈도를 지난 것으로 봅니다.
  그래서 이벤트가 적은 소스에서는 윈도가 끝나고 약 15분 뒤에 기록됩니다. 아직
  재생 중인 스트림은 아무리 오래 조용해도 이렇게 윈도를 지나지 않습니다. 재생이
  아직 따라잡지 못한 것이기 때문입니다.
- 윈도는 정책의 모든 스트림이 그 윈도를 지나야 기록됩니다. 그 전까지는 아직
  열리지 않은 스트림, 또는 아직 재생 중이면서 윈도의 끝에서 900초가 넘은 시각의
  이벤트를 아직 보내지 않은 스트림이 정책의 윈도를 열어 둡니다. 정책의 스트림
  중 열리지 않았거나 재생 중인 것이 있는 동안, Crusher는 10분마다 정책 ID,
  아직 열리지 않은 스트림 수, 열렸지만 아직 재생 중인 스트림 수를 경고로
  기록합니다.
- Crusher는 아직 기록하지 않은 가장 이른 윈도와 그다음 윈도를 함께 만듭니다.
  다른 센서보다 빨리 재생되는 경우처럼 그보다 더 앞선 이벤트를 보낸 스트림은
  다른 스트림이 따라올 때까지 멈춥니다. 이 스트림의 이벤트는 하나도 버려지지
  않습니다. 윈도가 900초보다 짧으면, 가장 이른 윈도의 끝에서 900초를 넘지 않은
  시각의 이벤트는 스트림을 멈추지 않고 바로 셉니다. 그 스트림은 아직 그 윈도를
  지나지 않았기 때문입니다. 이때 한 번에 만드는 윈도는 최대 2 + 900 / 윈도
  길이(소수점 이하 버림)개이며, 60초 윈도라면 17개입니다.
- 늦은 센서 묶음처럼 윈도가 기록된 뒤에 도착한 이벤트는 그 윈도를 보정합니다.
  Crusher는 그 윈도를 한 번 더 기록해 앞서 기록한 값을 대체합니다. 마지막으로
  기록한 윈도보다 오래된 이벤트는 버리고, 버린 이벤트 수를 경고로 기록합니다.
- 나누지 않는 정책은 이벤트가 없는 윈도를 기록하지 않습니다. 0으로 채운 행 대신
  빈 구간으로 보입니다. 나누는 정책은 그런 윈도에 표지를 기록합니다(아래 "윈도
  표지와 쓰기 세대" 참고).
- 진행 중인 윈도는 기록하지 않습니다. Crusher가 멈추거나 다시 연결하거나 정책이
  멈추면 진행 중인 윈도는 버려지고, 정책이 다시 실행될 때 Data Store에 저장된
  이벤트로 다시 만들어집니다. 이때 마지막으로 기록한 윈도도 한 번 더 기록합니다.
  센서의 스트림이 저절로 끝나면, Crusher가 다시 연결하거나 다시 시작할 때까지
  정책의 윈도는 기록되지 않습니다.
- 새 정책은 Data Store에 저장된 모든 이벤트로 만들어집니다.
- 정책의 출발지·목적지 주소 조건은 실시간 이벤트와 저장된 이벤트에 똑같이
  적용됩니다.

Crusher는 정책에 속한 모든 센서의 이벤트를 모두 더하며, 두 센서가 같은 통신을
보았는지 구별할 수 없습니다. 한 정책에 여러 센서를 지정할 때는 Crusher가
확인할 수 없는 다음 두 조건을 운영자가 책임지고 지켜야 합니다.

- 센서들이 감시하는 IP 주소가 겹치지 않습니다.
- 어떤 통신도 둘 이상의 센서에 보이지 않습니다. 두 센서가 모두 본 통신은 두 번
  셉니다.

## IP별 시계열

출발지나 목적지로 나누는 정책은 합산한 시계열 하나 대신 고객 내부 네트워크의
IP마다 시계열을 하나씩 기록합니다. 모든 IP의 윈도는 위의 규칙을 함께 따릅니다.

- 출발지로 나누는 정책은 이벤트의 출발지 주소로, 목적지로 나누는 정책은 목적지
  주소로 나눕니다. IP의 시계열 ID는 `P/IP`로, 정책 ID와 일반 표기법으로 쓴
  IP입니다. 예를 들어 `42/10.100.0.5`나 `42/2001:db8::1`입니다. IPv4 주소와
  그 주소를 IPv4 매핑한 IPv6 주소는 서로 다른 IP입니다. 나누는 정책은 정책
  자신의 ID `P`로 윈도의 표지만 기록하며(아래 참고), 나누지 않는 정책은 시계열
  하나를 `P`로 기록합니다.
- 나누는 쪽의 IP가 정책의 내부 네트워크에 있을 때만 이벤트를 셉니다. 내부
  네트워크의 호스트 중 하나이거나, 네트워크나 범위 중 하나에 속해야 합니다. 그
  쪽 IP가 외부인 이벤트는 시계열을 기록하지 않지만, 스트림이 윈도를 지나게
  하므로 윈도가 기록되게 할 수 있습니다.
- 정책의 상대 범위는 반대쪽 끝점을 거릅니다. 내부는 반대쪽도 내부 네트워크에
  있는 이벤트만, 외부는 반대쪽이 내부 네트워크 밖에 있는 이벤트만 세고, 전체는
  둘 다 셉니다. 나누지 않는 정책은 모든 상대를 세야 하며, 다른 범위를 가진
  정책은 정책 ID와 함께 경고를 남기고 건너뜁니다. Crusher가 아직 지원하지 않는
  고객 네트워크 단위로 나누는 정책도 마찬가지입니다.
- 같은 IP에 대한 정책의 모든 센서의 이벤트는 같은 시계열에 더합니다. 윈도를
  기록할 때는 모든 IP의 행을 시계열 ID의 오름차순으로 함께 기록합니다. 그래서
  이벤트가 뜸한 IP의 윈도도 그 IP의 다음 이벤트가 아니라 정책의 윈도가 닫힐 때
  기록됩니다. 윈도가 기록된 뒤에 도착한 이벤트는 그 IP의 행을 보정하고, 그
  윈도에 행이 없던 IP라면 행을 새로 추가합니다.
- 정책의 내부 네트워크만 바뀌면 정책을 다시 시작하지 않고 이어서 시작할 위치도
  버리지 않습니다. 새 네트워크는 정책이 받은 가장 최근 이벤트가 속한 윈도의
  다음 윈도부터 적용합니다. 그보다 앞선 윈도는 원래 네트워크를 유지하고, 이미
  기록한 행도 그대로 둡니다. 네트워크에 추가된 IP는 그 윈도부터 세고, 빠진 IP는
  그 윈도부터 윈도가 생기지 않습니다. 다시 시작하거나 다시 연결해 정책의
  스트림을 다시 요청하면, 정책이 이어서 시작하는 위치부터 모든 윈도에 현재
  네트워크를 적용합니다.
- 내부 네트워크가 비어 있는 나누는 정책은 이벤트를 세지 않습니다. Crusher는
  정책이 받은 첫 이벤트의 윈도부터, 네트워크가 비어 있는 동안 기록할 때가 된
  윈도마다 정책 ID와 함께 경고를 기록합니다. 정책은 계속 실행됩니다.
- 나누는 정책은 한 번에 최대 10,000개 IP의 시계열을 유지합니다. IP는 이벤트가
  도착한 순서대로 받아들이며, 아무리 조용해도 정책이 실행되는 동안 유지합니다.
  그 밖의 IP의 이벤트는 세지 않습니다. 그런 IP를 거절한 윈도를 기록할 때가
  되면, Crusher는 정책 ID와 거절한 IP 수를 경고로 기록합니다. 정책의 스트림을
  다시 요청하면 다시 재생된 이벤트에서 IP를 새로 받아들입니다.

## 윈도 표지와 쓰기 세대

나누는 정책은 기록한 윈도마다 완료 표지를 남겨, 읽는 쪽이 그 윈도의 IP 행을
모두 보고 있는지 지금까지 저장된 것만 보고 있는지 구별할 수 있게 합니다.
나누지 않는 정책은 표지도 세대도 기록하지 않습니다.

- 나누는 정책의 IP 행은 슬롯 값 뒤에 원소 하나를 더 가집니다. 그 행을 기록한
  실행의 쓰기 세대입니다.
- 윈도의 IP 행을 모두 기록한 뒤, Crusher는 같은 스트림으로 정책 자신의 ID `P`에
  윈도 시작 시각으로 윈도의 표지를 기록합니다. 표지는 윈도의 IP 행 수와 세대,
  두 값입니다. Data Store는 정책의 행을 Crusher가 보낸 순서대로 저장하므로,
  표지가 보이면 그 앞의 IP 행도 모두 보입니다. 읽는 쪽은 표지의 세대인 IP 행만
  씁니다. 같은 연결에서 정책의 스트림을 다시 요청하거나 삭제된 정책이 다시
  들어오면, Crusher는 이전 실행이 보낸 행을 Data Store가 모두 저장한 뒤에야 새
  실행의 행을 기록합니다. 그래서 이전 행이 새 행보다 나중에 저장되지 않습니다.
  10초가 지나도 저장되지 않으면 Crusher는 Data Store에 다시 연결합니다. Data
  Store에 다시 연결하기 전에도 Crusher는 이전 연결에서 보낸 것을 마무리하고,
  Data Store가 이를 저장할 때까지 시간 제한 없이 기다리며, 기다리는 동안 10초마다
  경고를 남깁니다. 이전 연결이 이미 끊겼거나 기다리는 중에 끊기면 Data Store가 그
  연결에서 받은 것을 저장했는지 Crusher가 알 수 없으므로, 더 기다리지 않고 다시
  연결합니다.
- Crusher는 정책의 스트림을 요청할 때마다 새 세대를 정합니다. 시작할 때, 정책이
  바뀌거나 정책 목록에 다시 들어올 때, Data Store에 다시 연결할 때입니다. 세대는
  요청 시점의 시계를 Unix 밀리초로 나타낸 값이며, 정책의 이전 세대에 1을 더한
  값이 더 크면 그 값입니다. 그래서 다시 시작하거나 시계가 뒤로 가도 세대는 늘
  커집니다. Crusher는 세대의 행을 기록하기 전에 세대를 `last_timestamp_data`
  파일에 저장합니다.
- 나누는 정책은 내부 네트워크가 비어 있는 윈도처럼 IP를 하나도 세지 않은
  윈도까지 모든 윈도를 닫고, 그 윈도에는 표지 `[0, 세대]`를 기록합니다. 이런
  윈도는 정책의 스트림 하나가 윈도의 끝에서 900초가 넘은 시각의 이벤트를 보낸
  뒤에야 닫힙니다. 재생이 끝난 조용한 스트림만으로는 닫히지 않으며, 그 뒤의
  윈도도 이 윈도를 기다립니다. 윈도는 시간 순서대로 닫힙니다. 새 정책은 처음
  받은 이벤트의 윈도보다 앞선 윈도에는 표지를 기록하지 않습니다.
- 정책의 스트림을 다시 요청하면, Crusher는 정책이 이어서 시작하는 윈도와 그
  뒤의 모든 윈도를 새 세대로 다시 기록합니다. IP 행을 먼저, 새 표지를 마지막에
  기록합니다. 내부 네트워크가 바뀐 경우처럼 새 실행이 더 이상 세지 않는 IP는 새
  행을 받지 않습니다. 그 IP의 이전 행은 이전 세대로 Data Store에 남으며, 새
  표지가 이를 제외합니다. 이제 IP 행이 없는 윈도는 `[0, 세대]`를 받습니다.
- 윈도의 표지를 기록한 뒤에 도착한 이벤트는 같은 세대로 그 IP의 행을 보정하며,
  표지는 다시 기록하지 않습니다. 그 윈도에 행이 없던 IP라면, Crusher는 새 행과
  그 행까지 센 표지 `[n + 1, 세대]`를 한 번의 쓰기로 함께 기록합니다. 다음
  윈도가 닫힐 때 Crusher는 정책 ID와, 직전 닫힘 이후 표지 뒤에 보정하거나 추가한
  IP 행 수를 경고로 기록합니다.

## 시작 직후 확인할 항목

- 프로세스가 즉시 종료되지 않는지 확인합니다.
